Módulo/Área:         Frontend / Refeições (modal "Editar refeição")
Severidade:          ALTO
Status:              ABERTO
Data:                2026-07-01

Descrição:
  No modal "Editar refeição", cada alimento tem um ícone de lixeira. Ao clicar
  na lixeira, o item é excluído IMEDIATAMENTE e de forma persistente (a chamada
  já vai ao backend), atualizando a tela principal na hora. Os botões
  "Cancelar" e "Salvar" não têm efeito sobre essa exclusão: mesmo clicando em
  "Cancelar", o item permanece excluído. Há ainda inconsistência visual: o item
  some da lista principal atrás do modal, mas continua aparecendo dentro do
  modal (o modal não reflete o estado já alterado).

Comportamento esperado:
  As edições no modal (remover itens, mudar tipo, notas) devem ser apenas
  locais/pendentes e só persistir quando o usuário clicar em "Salvar".
  "Cancelar" deve descartar todas as alterações e restaurar a refeição ao
  estado original. A tela principal só deve mudar após salvar.

Comportamento atual:
  Clicar na lixeira exclui o item de imediato no backend. "Cancelar" não
  desfaz. A lista principal já mostra a refeição sem o item, enquanto o modal
  ainda exibe o item removido (estado dessincronizado).

Passos para reproduzir:
  1. Tela "Refeições" > clicar no lápis (editar) de uma refeição
  2. No modal, clicar na lixeira de um alimento (ex: "macarrão")
  3. Observar que o item some da tela principal por trás do modal
  4. Clicar em "Cancelar"
  5. O item continua excluído (não foi restaurado)

Local:
  frontend/app/(dashboard)/refeicoes/page.tsx
  - Linha ~858: onClick da lixeira chama
    deleteMealItem.mutate({ mealId: editMeal.id, itemId: item.id })
    -> mutation persiste no backend imediatamente
  - Hook useDeleteMealItem (linha ~379)
  - handleSaveEdit / botões Cancelar (~882) e Salvar (~885)

Outras informações:
  Causa raiz: a remoção de item usa uma mutation imediata em vez de alterar um
  estado local (ex: lista de itens editável no state do modal). O modal também
  não é recarregado a partir do dado atualizado, causando a dessincronização
  visual.
  Sugestão de correção: manter os itens em estado local ao abrir o modal;
  a lixeira só remove do array local; "Salvar" envia o diff (itens removidos/
  alterados) ao backend; "Cancelar" descarta o estado local sem persistir.

BUG 10:
Título:              Notificações nunca são disparadas: INSERT falha por enum notificationtype (REMINDER vs reminder)
Módulo/Área:         Backend / Notificações e Lembretes (Celery worker)
Severidade:          ALTO
Status:              ABERTO
Data:                2026-07-01

Descrição:
  Lembretes são criados normalmente, o Celery Beat agenda e o worker executa a
  task dispatch_due_reminders a cada 60s, e o filtro de horário/dia funciona
  (a task casa o lembrete no minuto certo). PORÉM, ao criar a notificação in-app
  no banco, o INSERT falha com:
    invalid input value for enum notificationtype: "REMINDER"
  A task levanta exceção, tenta retry 3x, todas falham, e NENHUMA notificação é
  criada. Ou seja, a notificação não chega nem a existir dentro do próprio app
  (independente de Web Push / Telegram / WhatsApp). Afeta TODAS as notificações
  in-app, não só este lembrete.

Comportamento esperado:
  Quando um lembrete "bate o horário", uma notificação in-app é criada e aparece
  no sininho de Notificações.

Comportamento atual:
  A task casa o lembrete, mas o INSERT em notifications falha por incompatibi-
  lidade de enum. Nada é criado. UI mostra "Nenhuma notificação".

Passos para reproduzir:
  1. Criar um lembrete ativo para daqui a 1-2 min (qualquer tipo), todos os dias
  2. Aguardar o horário
  3. Nada aparece no sininho. Nos logs do worker:
     docker logs caloria_celery_worker | grep dispatch_due_reminders
     -> ERROR ... invalid input value for enum notificationtype: "REMINDER"

Local:
  backend/app/models/notification.py
    - NotificationType(StrEnum) valores minúsculos (REMINDER = "reminder", ...)
    - Coluna (linha ~32-33): SAEnum(NotificationType) SEM values_callable
  backend/app/workers/tasks/reminders.py
    - _send_reminder_notification cria Notification(type=NotificationType.REMINDER)
      (~linha 91-97)
  Enum no banco (notificationtype): labels em MINÚSCULO
    (reminder, daily_summary, weekly_report, hydration, system)

Causa raiz:
  Por padrão o SQLAlchemy persiste o NOME do membro do Enum ("REMINDER"), não o
  seu value ("reminder"). O tipo ENUM no Postgres foi criado com os VALUES
  (minúsculo). Logo, o SQLAlchemy envia "REMINDER" e o Postgres rejeita.
  (É a mesma família do BUG 1, mas no código de produção. Curiosamente os demais
  enums do banco — sex, mealtype, etc. — foram criados em MAIÚSCULO, casando com
  o nome do membro; o notificationtype é o outlier em minúsculo.)

Outras informações:
  Correção sugerida (uma das opções):
  (a) Preferida: configurar a coluna como
      SAEnum(NotificationType, values_callable=lambda e: [m.value for m in e])
      para o SQLAlchemy persistir os VALUES (minúsculo), casando com o banco.
      Verificar também a coluna 'type' de outras tabelas que usem StrEnum com
      values minúsculos (mesmo risco).
  (b) Alternativa: recriar o enum notificationtype no banco com labels em
      maiúsculo (via migração), alinhando ao comportamento padrão do SQLAlchemy.
  Observação: a task tem retry (max_retries=3) e depois desiste; corrigido o
  enum, o fluxo in-app deve voltar a funcionar. Web Push (VAPID) e canais
  externos (Telegram/WhatsApp) são caminhos separados e devem ser testados à
  parte depois. Relacionado a [BUG 1].
